# RAG chatbot design pipeline

## Scope and boundaries

The saved-context chatbot supports **fictional coursework scenarios only**. It
is not therapy, diagnosis, clinical monitoring, crisis support, or emergency
care. The application owns the paced-breathing/STOP sequences, exercise timing,
leave controls, and Crisis Support route. A model cannot alter them.

The chatbot may explain the prototype using its saved fictional conversation
context. It is instructed to remain concise and non-clinical. When it suggests
one approved practice, Vue displays an additional reviewed, application-owned
description of that practice and its controls. This detail is not generated by
the model and cannot alter an exercise sequence. FastAPI validates the
structure, cited IDs, skill allowlist, SQL plan, and persistence state; a
prompt alone is not the control boundary.

The source note is a deliberately small reviewed library, not live internet
search. Paced Breathing links to Bentley et al. (2023), *Breathing Practices
for Stress and Anxiety Reduction*, doi:10.3390/brainsci13121612. The wording
states that the review's programs were generally at least five minutes, so the
app's 60-second exercise is a brief practice rather than evidence of the
review's results. STOP links to Gasol et al. (2022), *Preventing Emotional
Dysregulation*, doi:10.3390/ijerph19010494. Its wording identifies the
underlying 30-lesson school program and its preliminary/mixed outcomes, so the
app does not equate its short walkthrough with that program. Both notes are
app-authored, static for the two approved skills, and excluded from the model
prompt, stored chat messages, and user profile.

## Responsibilities

| Layer | Files | Responsibility |
| --- | --- | --- |
| Vue view | `frontend/src/App.vue`, `frontend/src/api.js` | Starts chats, displays saved messages/record IDs, handles loading/failure, and never reads a provider key. |
| API/controller | `backend/app/main.py` | Validates HTTP bodies, saves state, applies idempotency, scopes retrieval, and returns truthful errors. |
| Model adapter | `backend/app/rag.py` | Calls OpenAI Responses in explicit `openai` mode, requests strict JSON, and validates untrusted outputs. |
| SQLite model | `backend/app/database.py` | Creates conversations, messages, RAG-request audit tables, and the separate daily-mood table. |

## Local data model

`conversations` has a stable ID and created/updated timestamps. `messages` has
a stable ID, conversation ID, client message ID, role, content, status,
suggested skill, cited record IDs, and timestamp. A unique
`(conversation_id, client_message_id)` constraint rejects a repeated browser
submission. `rag_requests` records the plan outcome, allowed SQL template, and
retrieved message IDs.

This assignment version deliberately retains the full content of fictional chat
messages so it can reconstruct a conversation and use it as RAG context. The
existing optional skills check-in remains a separate, privacy-minimizing flow;
it does not retain its raw text. Live OpenAI mode sends a submitted fictional
chat message and its retrieved local context to OpenAI. Clear saved chats from
the chatbot UI or `DELETE /api/conversations`.

The optional Profile reflection is excluded from those stored records. Only
after a person explicitly selects **Use selected responses in Check-in Chat**
does the next chat request carry selected response labels. The application
uses them once in an app-owned two-practice rule, discards them before the
request completes, and neither writes them to SQLite nor sends them to OpenAI.

`mood_entries` is separate from conversations and contains only `day`, one
allowlisted label, and `updated_at`. It accepts no note text and is never part
of the SQL RAG retrieval schema, practice-context summary, or model input.

## Two-call SQL RAG flow

1. `POST /api/conversations/{id}/messages` validates a 1–800 character message
   plus a client-generated idempotency ID. An optional reflection object accepts
   only the four known response labels and is not part of the database schema.
   The endpoint saves only the user message as `pending`.
2. A short standalone greeting, or a request with explicit transient reflection
   responses, uses an application-owned retrieval plan and reply. For other
   messages, the first model call receives the question and the small
   database-schema contract. It returns strict JSON with `sql` and `limit`.
3. `backend/app/rag.py` accepts only its one exact `SELECT` template and a
   limit of 4 or 6. FastAPI binds the current conversation ID and limit; it
   never interpolates model output or message content into SQL.
4. FastAPI executes that read-only query through its normal SQLite connection,
   reverses the selected rows to chronological order, and records their IDs.
5. For a short greeting, the application returns its fixed opening message. For
   an explicit transient reflection request, application code selects Paced
   Breathing when body tension or feeling on edge is “Mostly” or “Very much”;
   otherwise it selects STOP. It returns a fixed neutral acknowledgement and
   never sends the labels to the model. Otherwise, the second model call
   receives the question, reviewed skill boundaries, and the retrieved
   ID/role/content/timestamp records. It returns strict JSON with `reply`, an
   allowlisted `suggested_skill`, and cited message IDs.
6. FastAPI accepts only a 1–360 character reply whose cited IDs are from the
   retrieved rows. One transaction changes the user message to `complete`,
   saves the assistant reply, and records the completed RAG request.

The model never connects to SQLite and does not receive an unconstrained query
tool. This deliberately narrow query set demonstrates model-planned,
application-validated SQL retrieval without permitting writes, cross-chat
access, unbounded rows, or raw SQL execution.

## Failure contract

| Condition | Stored state | API/UI outcome |
| --- | --- | --- |
| Duplicate client message ID | No second model call or duplicate row. | `409`; reload the saved chat. |
| Missing key, timeout, provider failure, refusal, or invalid reply | User message becomes `failed`; no assistant message is saved. | `503`; calm fallback and Crisis Support remain usable. |
| Unsafe SQL plan | User message becomes `failed`; audit records `rejected`; no query runs. | `502`; no fabricated assistant reply. |
| SQLite write/retrieval failure | No success is reported. | `503` with app-owned error wording. |
| Mock mode | Deterministic allowed plan/reply is saved. | Routine tests need no key or network. |

## API contract

| Endpoint | Validated input | Successful result |
| --- | --- | --- |
| `POST /api/conversations` | `{}` | New conversation ID and timestamps. |
| `GET /api/conversations` | None | Up to 12 local conversation summaries. |
| `GET /api/conversations/{id}` | Conversation ID | Ordered saved messages and statuses. |
| `POST /api/conversations/{id}/messages` | `content` (1–800 chars), `client_message_id` (8–100 chars), and optional allowlisted one-request reflection labels | Ordered conversation including validated assistant reply; the optional reflection labels are not stored. |
| `DELETE /api/conversations` | None | Removes all local saved conversations/messages/RAG audit rows. |
| `GET /api/moods?month=YYYY-MM` | Month key | Selected daily labels for the visible month only. |
| `PUT /api/moods/YYYY-MM-DD` | One allowlisted `mood` label; no extra fields | Creates or replaces one chosen label for that day. |
| `DELETE /api/moods/YYYY-MM-DD` | Day key | Removes the selected day's label. |
| `DELETE /api/moods` | None | Removes all daily mood labels. |

## Worked fictional example

For “In this fictional scenario, which short skill is available?”, mock mode
saves the user message, retrieves its current conversation row with the
allowlisted `SELECT`, and saves an assistant reply citing that row’s ID. Live
mode follows the same database path but uses two bounded OpenAI Responses API
calls. The UI displays the cited record ID next to the assistant message so a
reviewer can compare it with SQLite.

OpenAI Structured Outputs is requested with `text.format` and a strict JSON
Schema; the application still validates the output and handles refusal/partial
output as a provider failure. [Official OpenAI Structured Outputs
documentation](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)
describes this schema-shaped Responses API format.

## Live audio session boundary — mocked WebRTC and input-mute control

The live-audio increments keep the existing saved text-chat/RAG flow separate
from optional voice use. `frontend/src/voice.js` owns native browser media and
WebRTC work; `frontend/src/App.vue` owns its visible Chat-screen state. Voice
audio, transcripts, and Live-session data have no SQLite tables and are not
written to the application database. Routine checks use injected browser and
FastAPI mocks; no actual microphone permission or provider call was used.

| Endpoint | Validated input | Successful response | Failure behavior |
| --- | --- | --- | --- |
| `GET /api/voice/config` | None | `configured` and a 1–300 second maximum only | Never returns a key, model name, provider URL, or provider error. |
| `POST /api/voice/sessions` | One browser-generated SDP offer, 1–65,536 characters | Validated session ID, SDP answer, and the maximum duration | Rejects extra browser configuration and invalid offers; returns an app-owned text-chat fallback for missing configuration, provider failure, or malformed provider data. |

`backend/app/voice.py` owns `gpt-live-1`, the configured `gpt-6-luna`
Responses-delegation model, the provider URL, the two reviewed prompt roles,
`store: false`, no-tools policy, finite 2–15 second timeout, and response
validation. The short Live prompt controls neutral spoken behavior; the
detailed delegated prompt holds the prototype boundaries. The latter sets
`tool_choice: "none"` and registers no hosted or custom tools, so neither model
can execute actions or alter app state. The reviewed prompt copy is in
`prompts/02-gpt-live-roles.md`. This matches OpenAI's documented separation of
the spoken Live model from an independently chosen Responses-delegation model:
[GPT-Live delegation guide](https://developers.openai.com/api/docs/guides/live-delegation).

FastAPI makes one unretried HTTPS request to `POST /v1/live/sessions`; Vue
cannot choose any role, model, instruction, tool, duration, or provider field.
The session payload configures the browser data channel with a least-privilege
allowlist: it can send only `session.input_audio.mute` and
`session.input_audio.unmute`, and it receives only startup, closure, those two
matching acknowledgements, and generic errors. It cannot send session updates,
instructions, tool commands, or exercise/crisis controls.
`VOICE_LIVE_AUDIO_ENABLED` must be exactly `1`, `true`, or `yes` in the ignored
server environment before FastAPI treats voice as configured. This remains off
by default, including when a local API key is present. The provider result is
reduced to the session ID and SDP answer. `store: false` is a session
forking/recording setting, not a general retention claim.

The mocked WebRTC flow starts only after explicit microphone selection. It
recognizes only `session.started`, `session.closed`, the matching
`session.input_audio.muted`/`session.input_audio.unmuted` acknowledgements, and
`error` lifecycle events; it ignores transcript/debug events. Crisis Support,
exercise controls, and all navigation remain application-owned. No audio,
transcript, or live-session payload is stored by this application.

### Mocked browser connection contract

From an explicit **Start voice** action, Vue checks the safe configuration
status, requests `getUserMedia({ audio: true, video: false })`, creates an
`oai-events` data channel before its offer, waits for ICE gathering, posts only
the resulting SDP to FastAPI, then applies the validated answer. The panel uses
the states `idle`, `permission`, `connecting`, `active`, `muting`, `muted`,
`unmuting`, `closing`, `closed`, and `error`. It becomes active only after the
allowlisted `session.started` event. From active, the **Mute microphone** action
sends `session.input_audio.mute` with an ephemeral event ID and displays muted
only after its matching acknowledgement; **Unmute microphone** follows the
same pattern. A received track is attached to an in-memory audio element; an
autoplay rejection reveals a user-gesture **Enable assistant audio** action.
Transcript and unexpected event payloads are ignored and never displayed or
stored.

No user-facing End control exists yet. The controller does stop local
microphone tracks and close its peer connection if Chat is abandoned,
the app navigates away, Crisis Support opens, or Vue unmounts. Step 5 will add
the complete End protocol—send `session.close`, briefly wait for
`session.closed`, and then clean up—plus focused duplicate/late-result tests.
